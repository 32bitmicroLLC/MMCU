# RP2040/RP2350 Target Integration

This document describes the `rp2040` and `rp2350` targets under
`MMCU_PLATFORM=pico_sdk` (see
[Configure: Platform, Target, Toolchain](../configure.md)). Both targets
build against one of two foundations, selected by `MMCU_RP2_FOUNDATION`
(`configure.sh --rp2-foundation`):

| `MMCU_RP2_FOUNDATION` | default? | foundation | compilers |
|---|---|---|---|
| `pico-sdk` | yes | vendored pico-sdk: real boot2, clock tree, linker script | gcc only |
| `cmsis` | no | hand-rolled startup/linker, CMSIS-Core only | gcc, clang |

```bash
./configure.sh --platform pico_sdk --target rp2040                        # pico-sdk foundation (default)
./configure.sh --platform pico_sdk --target rp2350 --rp2-foundation cmsis --compiler clang
```

## `pico-sdk` foundation (default)

Requires the vendored pico-sdk checkout: run
`./platforms/pico-sdk/pico-sdk-install.sh` first (see
[Bare-Metal pico-sdk Platform](../platforms-baremetal/pico-sdk.md)) — configure
fails with a clear `FATAL_ERROR` pointing at that script if it's missing.

`mmcu_app` links against pico-sdk's own `pico_runtime` and
`pico_standard_link` targets, giving it:

- **A real, checksummed boot2 stage** (RP2040) or sealed/signed image header
  (RP2350) at the start of flash — this is a genuinely bootable image, not a
  compile-only exercise. Verified: `readelf -S` shows a real `.boot2` section
  at `0x10000000` for `rp2040`; `rp2350`'s picobin-format image embeds the
  equivalent directly in `.text`.
- **Real clock-tree bring-up.** `pico_runtime`'s `runtime_init()` configures
  XOSC/PLL/`clk_sys`/`clk_peri` before calling `main`, replacing every other
  target's do-nothing `SystemInit()`.
- **CMSIS is not used at all** here — pico-sdk supplies its own register
  headers/core support for both RP2040 (Cortex-M0+) and RP2350 (Cortex-M33).
- `MMCU_TARGET=rp2040` selects `PICO_PLATFORM=rp2040`/`PICO_BOARD=pico`;
  `rp2350` selects `PICO_PLATFORM=rp2350-arm-s`/`PICO_BOARD=pico2`.
- `picotool` (needed to seal/sign RP2350 images) reuses the one already
  installed by `pico-sdk-install.sh` instead of being fetched/built again.

**gcc only for now.** pico-sdk's C sources include real libc headers
(newlib/picolibc), and plain `clang-20` (unlike `arm-none-eabi-gcc`) doesn't
locate those without a properly configured ARM clang runtime/sysroot — e.g.
the LLVM Embedded Toolchain for Arm. `configure.sh`/`CMakeLists.txt` reject
`--rp2-foundation pico-sdk --compiler clang` with a clear error up front
rather than failing deep inside pico-sdk's own build with a confusing
`sys/cdefs.h not found`. Use `--rp2-foundation cmsis` for clang.

**Still not implemented**, deferred as genuinely separate follow-up work:

- **No QEMU machine.** `qemu-system-arm -machine help` has no RP2040/RP2350
  entry (only full Raspberry Pi SoCs, unrelated silicon), so
  [Run](../run.md) has no dispatch target for these builds — verified by
  compiling/linking only.
- **`gpio0`/`uart0` are still the shared generic placeholder objects** from
  `src/gpio.cppm`/`src/uart.cppm` (fake in-memory registers), not real
  RP2040/RP2350 SIO/UART addresses, and `mmcu_app` does not link against
  pico-sdk's `hardware_gpio`/`hardware_uart` (per the "no vendor HAL" rule —
  see [Bare-Metal pico-sdk Platform](../platforms-baremetal/pico-sdk.md)).
  Wiring in real SIO-based GPIO is straightforward (a flat, bit-per-pin
  register set that maps directly onto `mmcu::gpio::layout`); real PL011
  UART does not fit `mmcu::uart::layout`/`configure()` as-is, since its baud
  rate is a clock-divisor pair (`UARTIBRD`/`UARTFBRD`), not a raw value
  written to one register. Left for a follow-up target-specific
  default-object pass (see [Target Module Objects](../target-modules.md)).
- Multicore (core1), USB, and other pico-sdk features beyond
  `pico_runtime`/`pico_standard_link` are not linked in.

## `cmsis` foundation (`--rp2-foundation cmsis`)

The original first-pass implementation, kept as a fallback for anyone who
wants gcc *or* clang without vendoring pico-sdk at all. Follows the exact
same integration pattern as
[ARM Cortex-M0/M0+ Target Integration](cortex-m0-m0plus.md): CMSIS-Core plus
hand-rolled startup/linker script, no vendor HAL, no vendored pico-sdk
required.

- Real CPU core selection: `rp2040` → Cortex-M0+, `rp2350` → Cortex-M33.
- Real memory maps taken from the datasheets: XIP flash base `0x10000000`,
  main SRAM base `0x20000000` (256K for RP2040, a conservative 512K subset
  of RP2350's 520K).
- A minimal vector table, `Reset_Handler` (`.data`/`.bss` init, calls
  `SystemInit`, C++ static constructors, `main`), `Default_Handler` trap
  loop — the same shape as `cortex_m0`/`cortex_m0plus`.
- `SystemInit()` only does `__DSB()`/`__ISB()` — no clock-tree bring-up.
- **No boot2.** `.isr_vector` is placed directly at `0x10000000` with no
  checksummed stage-2 image, so it will not boot from flash on real
  hardware — this foundation verifies compile/link correctness only.

### RP2350 CMSIS configuration

`system_rp2350.c` defines the CMSIS `core_cm33.h` device macros explicitly,
rather than relying on its warned-about defaults:

```c
#define __CM33_REV 0x0000U
#define __FPU_PRESENT 0U
#define __DSP_PRESENT 1U
#define __MPU_PRESENT 1U
#define __SAUREGION_PRESENT 0U
#define __VTOR_PRESENT 1U
#define __NVIC_PRIO_BITS 3U
```

`__DSP_PRESENT` must be `1`: `arm-none-eabi-gcc -mcpu=cortex-m33` generates
DSP (SIMD) instructions by default (RP2350's Cortex-M33 does include the DSP
extension), and CMSIS-Core hard-errors if code is compiled with DSP
instructions while `__DSP_PRESENT` says otherwise. `__FPU_PRESENT` is `0`
and the toolchain adds `-mfloat-abi=soft` since nothing here uses floating
point. `__SAUREGION_PRESENT` is `0`: TrustZone/SAU setup is not attempted.

## Files

```text
targets/
  arm/
    rp2040/
      rp2040.cppm
      startup_rp2040.s      # cmsis foundation only
      system_rp2040.c       # cmsis foundation only
      linker.ld             # cmsis foundation only
    rp2350/
      rp2350.cppm
      startup_rp2350.s      # cmsis foundation only
      system_rp2350.c       # cmsis foundation only
      linker.ld             # cmsis foundation only
```

`rp2040.cppm`/`rp2350.cppm` (trivial identity marker modules) are used by
both foundations; the startup/system/linker files are only used for
`--rp2-foundation cmsis`.

## A shared toolchain-file lesson

Both foundations use `cmake/toolchains/arm-none-eabi-{gcc,clang}.cmake` (see
[Configure: Platform, Target, Toolchain](../configure.md)). Getting the
`pico-sdk` foundation working surfaced a real bug in those files: they used
to inject `-ffreestanding`/`-nostdlib`/`--gc-sections`/the linker entry
symbol via `CMAKE_*_FLAGS_INIT`, which seeds CMake's *global*
`CMAKE_C_FLAGS`/`CMAKE_EXE_LINKER_FLAGS` — applying to **every**
`add_executable()` in the whole build, not just `mmcu_app`. That's invisible
with a single-executable build (`cortex-m0`/`cortex-m0plus`/`cmsis`
foundation), but pico-sdk's own `add_subdirectory()` tree defines its own
executables (e.g. `boot_stage2`'s `bs2_default`), and those flags broke it —
first by overriding its entry symbol, then by garbage-collecting its output
down to zero sections. The fix: only `-mcpu`/`-mthumb` are global; everything
else is applied with `target_compile_options()`/`target_link_options()`
scoped to `mmcu_app` alone (`mmcu_apply_freestanding_options()` in
`CMakeLists.txt`), which can never leak into unrelated targets pico-sdk adds
underneath it.
