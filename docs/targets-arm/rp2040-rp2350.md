# RP2040/RP2350 Target Integration

This document describes the `rp2040` and `rp2350` targets under
`MMCU_PLATFORM=pico_sdk` (see
[Configure: Platform, Target, Toolchain](../configure.md)). They follow the
exact same integration pattern as
[ARM Cortex-M0/M0+ Target Integration](cortex-m0-m0plus.md): CMSIS-Core plus
hand-rolled startup/linker script, first pass, no vendor HAL.

## Scope

What's implemented:

- Real CPU core selection: `rp2040` targets Cortex-M0+ (RP2040's core),
  `rp2350` targets Cortex-M33 (the RP2350 Arm core variant), both via
  `cmake/toolchains/arm-none-eabi-{gcc,clang}.cmake` (see
  [Configure: Platform, Target, Toolchain](../configure.md)).
- Real memory maps taken from the RP2040/RP2350 datasheets: XIP flash base
  `0x10000000`, main SRAM base `0x20000000` (256K for RP2040, a conservative
  512K subset of RP2350's 520K for RP2350).
- A minimal vector table, `Reset_Handler` (`.data`/`.bss` init, calls
  `SystemInit`, C++ static constructors, `main`), and `Default_Handler` trap
  loop for every other exception — the same shape as `cortex_m0`/
  `cortex_m0plus`.
- CMSIS-Core (`core_cm0plus.h`, `core_cm33.h`) via the same `MMCU_CMSIS_DIR`/
  `mmcu_require_cmsis()` mechanism as the Cortex-M0/M0+ targets — **not**
  pico-sdk's vendored copy.

What's explicitly **not** implemented (deferred, same spirit as
Cortex-M0/M0+'s deferred SVD support):

- **No boot2 / second-stage bootloader.** RP2040/RP2350's ROM bootloader
  requires a checksum-validated 256-byte stage-2 image at the start of QSPI
  flash before it will jump anywhere. `.isr_vector` is placed directly at
  `0x10000000` instead, so this will not boot from flash on real hardware —
  compile/link correctness is what's verified here, not booting.
- **No clock-tree bring-up.** `SystemInit()` only does `__DSB()`/`__ISB()`,
  same as every other target. RP2040/RP2350 peripherals (including UART)
  need the XOSC/PLL/`clk_sys`/`clk_peri` chain configured before they'll
  actually run; that isn't done here.
- **No QEMU machine.** `qemu-system-arm -machine help` has no RP2040/RP2350
  entry (only full Raspberry Pi SoCs, which are unrelated silicon), so
  [Run](../run.md) has no dispatch target for these builds — they're
  compile/link-verified only, the same way `cortex-m0`/`cortex-m0plus` are
  not yet exercised on real hardware either.
- **`gpio0`/`uart0` are still the shared generic placeholder objects** from
  `src/gpio.cppm`/`src/uart.cppm` (fake in-memory registers), not real
  RP2040/RP2350 register addresses — exactly matching `cortex-m0`/
  `cortex-m0plus`'s current state. Wiring in real SIO-based GPIO is
  straightforward (RP2040/RP2350's SIO block is a flat, bit-per-pin register
  set that maps directly onto `mmcu::gpio::layout`), but real PL011 UART
  does not: its baud rate is a clock-divisor pair (`UARTIBRD`/`UARTFBRD`),
  not a raw value written to one register the way
  `mmcu::uart::layout`/`configure()` currently assumes. Both are left for a
  follow-up target-specific default-object pass (see
  [Target Module Objects](../target-modules.md)), not attempted here.

## Why this counts as "resolved" rather than deferred

Before this integration, `MMCU_TARGET=rp2040`/`rp2350` under
`MMCU_PLATFORM=pico_sdk` failed configure immediately with a `FATAL_ERROR`.
Both targets now configure and build successfully — verified with both
`gcc` and `clang` — producing a linked ELF with the correct CPU
(`Tag_CPU_name: Cortex-M0+` / `Cortex-M33`) and entry point
(`Reset_Handler` at the flash base). What remains (boot2, clocks, real
GPIO/UART addresses) is genuinely separate follow-up work, not a blocker for
"can I configure/build this target."

## Build

```bash
./configure.sh --platform pico_sdk --target rp2040
./build.sh --build-dir build-rp2040-gcc

./configure.sh --platform pico_sdk --target rp2350 --compiler clang
./build.sh --build-dir build-rp2350-clang
```

## RP2350 CMSIS configuration

`system_rp2350.c` defines the CMSIS `core_cm33.h` device macros explicitly,
rather than relying on its warned-about defaults:

```c
#define __CM33_REV 0x0000U
#define __FPU_PRESENT 0U
#define __DSP_PRESENT 1U
#define __MPU_PRESENT 1U
#define __SAUREGION_PRESENT 0U
#define __VTOR_PRESENT 1U
#define __NVIC_PRIO_BITS 3U
```

`__DSP_PRESENT` must be `1`: `arm-none-eabi-gcc -mcpu=cortex-m33` generates
DSP (SIMD) instructions by default (RP2350's Cortex-M33 does include the DSP
extension), and CMSIS-Core hard-errors if code is compiled with DSP
instructions while `__DSP_PRESENT` says otherwise. `__FPU_PRESENT` is `0`
and the toolchain adds `-mfloat-abi=soft` (see
[Configure: Platform, Target, Toolchain](../configure.md)) since nothing
here uses floating point. `__SAUREGION_PRESENT` is `0`: TrustZone/SAU setup
is not attempted.
