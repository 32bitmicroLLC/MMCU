# RP2040/RP2350 Target Integration

RP2040/RP2350 support has two active platform foundations (see
[Configure: Platform, Target, Toolchain](../configure.md)):

| `MMCU_PLATFORM` | `MMCU_TARGET` | chip/core | foundation | compilers |
|---|---|---|---|---|
| `pico_sdk` | `rp2040` (default) | RP2040, Cortex-M0+ | vendored pico-sdk: real boot2, clock tree, linker script | gcc only |
| `pico_sdk` | `rp2350` | RP2350, Cortex-M33 | vendored pico-sdk: real boot2, clock tree, linker script | gcc only |
| `cmsis` | `rp2040` | RP2040, Cortex-M0+ | CMSIS-Core plus Raspberry Pi CMSIS-RP2xxx-DFP startup/system/header/linker files | gcc or clang |

```bash
./configure.sh --platform pico_sdk --target rp2040               # real pico-sdk boot2/clocks (default)
./configure.sh --platform cmsis --target rp2040 --board pico      # CMSIS-RP2xxx-DFP path
```

## `rp2040`/`rp2350` (pico-sdk foundation)

Requires the vendored pico-sdk checkout: run
`./platforms/pico-sdk/pico-sdk-install.sh` first (see
[Bare-Metal pico-sdk Platform](../platforms-baremetal/pico-sdk.md)) — configure
fails with a clear `FATAL_ERROR` pointing at that script if it's missing.

`mmcu_app` links against pico-sdk's own `pico_runtime` and
`pico_standard_link` targets, giving it:

- **A real, checksummed boot2 stage** (RP2040) or sealed/signed image header
  (RP2350) at the start of flash — this is a genuinely bootable image, not a
  compile-only exercise. Verified: `readelf -S` shows a real `.boot2` section
  at `0x10000000` for `rp2040`; `rp2350`'s picobin-format image embeds the
  equivalent directly in `.text`.
- **Real clock-tree bring-up.** `pico_runtime`'s `runtime_init()` configures
  XOSC/PLL/`clk_sys`/`clk_peri` before calling `main`, replacing every other
  target's do-nothing `SystemInit()`.
- **CMSIS is not the selected platform here.** pico-sdk supplies the boot,
  link, runtime, and chip-support foundation for both chips. If pico-sdk
  internally uses CMSIS-style headers, that is a pico-sdk implementation
  detail, not `MMCU_PLATFORM=cmsis`.
- `MMCU_TARGET=rp2040` selects `PICO_PLATFORM=rp2040`/`PICO_BOARD=pico`;
  `rp2350` selects `PICO_PLATFORM=rp2350-arm-s`/`PICO_BOARD=pico2`.
- `picotool` (needed to seal/sign RP2350 images, and to convert to `.uf2`)
  reuses the one already installed by `pico-sdk-install.sh` instead of
  being fetched/built again.
- **Output is `mmcu_app.elf`, not a bare `mmcu_app`**, plus `mmcu_app.uf2`
  (the flashable image), `.bin`, `.hex`, `.dis`, and `.elf.map` —
  `pico_add_extra_outputs(mmcu_app)`'s post-build picotool processing.
  `pico_sdk_init()` sets `CMAKE_EXECUTABLE_SUFFIX=.elf`, but that runs after
  `add_executable(mmcu_app)` already created the target, too late to take
  effect on its own — `CMakeLists.txt` sets the `SUFFIX` property on
  `mmcu_app` directly instead, since picotool's uf2/bin/hex conversion needs
  a recognized file extension to identify the ELF input. `build.sh`/`run.sh`
  look for both `mmcu_app` and `mmcu_app.elf`.

**gcc only for now.** pico-sdk's C sources include real libc headers
(newlib/picolibc), and plain `clang-20` (unlike `arm-none-eabi-gcc`) doesn't
locate those without a properly configured ARM clang runtime/sysroot — e.g.
the LLVM Embedded Toolchain for Arm. `configure.sh`/`CMakeLists.txt` reject
`MMCU_PLATFORM=pico_sdk` with `MMCU_TARGET=rp2040`/`rp2350` and
`--compiler clang` up front with a clear error, rather than failing deep
inside pico-sdk's own build with a confusing `sys/cdefs.h not found`.
This restriction is specific to the pico-sdk platform. The CMSIS `rp2040`
target does not build pico-sdk and can use the normal CMSIS GCC or Clang
toolchain files.

**Still not implemented**, deferred as genuinely separate follow-up work:

- **No QEMU machine.** `qemu-system-arm -machine help` has no RP2040/RP2350
  entry (only full Raspberry Pi SoCs, unrelated silicon), so
  [Run](../run.md) has no dispatch target for these builds — verified by
  compiling/linking only.
- **The core peripheral defaults are still shared generic placeholder
  objects** from `src/core/` (fake in-memory registers), not real
  RP2040/RP2350 SIO/UART/I2C/SPI/ADC addresses, and `mmcu_app` does not link against
  pico-sdk's `hardware_gpio`/`hardware_uart`/`hardware_i2c`/`hardware_spi`/`hardware_adc` (per the "no vendor HAL" rule —
  see [Bare-Metal pico-sdk Platform](../platforms-baremetal/pico-sdk.md)).
  Wiring in real SIO-based GPIO is straightforward (a flat, bit-per-pin
  register set that maps directly onto `mmcu::gpio::layout`); real PL011
  UART does not fit `mmcu::uart::layout`/`configure()` as-is, since its baud
  rate is a clock-divisor pair (`UARTIBRD`/`UARTFBRD`), not a raw value
  written to one register. Left for a follow-up target-specific
  default-object pass (see [Target Module Objects](../target-modules.md)).
- **Pico-specific modules exist as MMCU interfaces, not real register
  bindings yet.** `modules/pico/` and `src/pico/` define `pico.pio`,
  `pico.sio`, `pico.multicore`, and, for RP2350 only, `pico.hstx`.
  CMake compiles those modules only for `rp2040`/`rp2350` family targets,
  but their implementation is still placeholder state rather than real
  pico-sdk `hardware_pio`/`hardware_sync`/multicore/HSTX integration.
- USB and other pico-sdk features beyond `pico_runtime`/`pico_standard_link`
  are not linked in.

## `rp2040` (CMSIS-RP2xxx-DFP foundation)

`MMCU_PLATFORM=cmsis` with `MMCU_TARGET=rp2040` uses Raspberry Pi's
CMSIS-RP2xxx-DFP checkout directly. It is a CMSIS path, not a pico-sdk path:

- CMSIS-Core headers come from `platforms/cmsis/CMSIS_6`.
- RP2040 device headers, `SystemInit()`, startup, and linker script come
  from `platforms/cmsis/CMSIS-RP2xxx-DFP/CMSIS/Device/RP2040`.
- MMCU supplies only a tiny `_start` bridge in
  `targets/arm/rp2040/cmsis_runtime.c` so the DFP startup can enter the
  freestanding `mmcu_app` without linking a C library startup object.
- Compatible boards are the RP2040 Pico declarations: `pico`, `pico-h`,
  `pico-w`, `pico-wh`, `pico-all`, and `pico-w-all`.

The current Raspberry Pi DFP revision wired here provides RP2040 device
files. It does not provide an active RP2350/Pico 2 CMake path in MMCU; use
`MMCU_PLATFORM=pico_sdk` for RP2350.

## Files

```text
targets/
  arm/
    rp2040/
      rp2040.cppm             # used by rp2040
      cmsis_runtime.c         # _start bridge for CMSIS-RP2xxx-DFP startup
      startup_rp2040.s        # currently unused; old hand-rolled experiment
      system_rp2040.c         # currently unused; old hand-rolled experiment
      linker.ld               # currently unused; old hand-rolled experiment
    rp2350/
      rp2350.cppm             # used by rp2350
      startup_rp2350.s        # currently unused; old hand-rolled experiment
      system_rp2350.c         # currently unused; old hand-rolled experiment
      linker.ld               # currently unused; old hand-rolled experiment
```

`rp2040.cppm`/`rp2350.cppm` are trivial identity marker modules for the
active RP-family targets. The old hand-written RP2040/RP2350
startup/system/linker files remain in tree as reference material from the
old experiment, but configured CMSIS RP2040 builds use the Raspberry Pi DFP
startup/system/linker files instead.

Pico-specific module specs and C++20 interfaces live separately from
portable core modules:

```text
modules/pico/
  pio/mmcu.yaml
  sio/mmcu.yaml
  multicore/mmcu.yaml
  hstx/mmcu.yaml          # RP2350 only
src/pico/
  pio.cppm
  sio.cppm
  multicore.cppm
  hstx.cppm               # RP2350 only
```

These are intentionally not under `modules/core/`: PIO and SIO are
RP-series concepts, HSTX is RP2350-specific, and the multicore interface
starts with the RP-series launch/FIFO model rather than claiming to be a
portable MCU abstraction.

## A shared toolchain-file lesson

The active bare-metal targets use `cmake/toolchains/arm-none-eabi-{gcc,clang}.cmake` (see
[Configure: Platform, Target, Toolchain](../configure.md)). Getting `rp2040`/
`rp2350`'s pico-sdk foundation working surfaced a real bug in those files:
they used to inject `-ffreestanding`/`-nostdlib`/`--gc-sections`/the linker
entry symbol via `CMAKE_*_FLAGS_INIT`, which seeds CMake's *global*
`CMAKE_C_FLAGS`/`CMAKE_EXE_LINKER_FLAGS` — applying to **every**
`add_executable()` in the whole build, not just `mmcu_app`. That's invisible
with a single-executable build (`cortex-m0`/`cortex-m0plus`/the `-cmsis`
targets), but pico-sdk's own `add_subdirectory()` tree defines its own
executables (e.g. `boot_stage2`'s `bs2_default`), and those flags broke it —
first by overriding its entry symbol, then by garbage-collecting its output
down to zero sections. The fix: only `-mcpu`/`-mthumb` are global; everything
else is applied with `target_compile_options()`/`target_link_options()`
scoped to `mmcu_app` alone, which can never leak into unrelated targets
pico-sdk adds underneath it.
